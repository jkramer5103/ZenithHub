# ZenithHub: Multi-Account Web UI (hard fork of ZenithProxy)

Status: design settled 2026-10-28. This document is the source of truth for the revamp. Renamed
from ZenithProxy to ZenithHub on 2026-10-29: user-facing names only, code keeps `com.zenith` and `ZENITH_*`.

## Goals

- Run everything with one `docker compose up`: a single container and a single data volume.
- Manage many Minecraft accounts from a web UI. Adding an account is a single device-code click.
- Let one account run on several servers at the same time. Each (account, server) pair is an **instance**.
- Give players one public Minecraft port with an in-game lobby: a chest GUI of the instances you may use; click to join, `/lobby` to return.
- Offer an optional central Discord bot. Discord is never required.

## Architecture

```
            ┌──────────────────────── container ─────────────────────────┐
 browser ──►│ manager (Java)                                             │
  :8080     │  ├─ web UI (SvelteKit static) + REST/WebSocket API         │
            │  ├─ auth: admin + users + grants (one permission system)   │
            │  ├─ account service: device code, import, offline, refresh │
            │  ├─ supervisor: 1 Zenith process per instance              │
            │  ├─ lobby + router on the public MC port                   │
            │  └─ central Discord bot (optional)                         │
 MC client ►│       │ localhost control API + stdout                     │
  :25565    │       ▼                                                    │
            │ zenith (linux native) × N   ── each in /data/instances/<id>│
            └────────────────────────────────────────────────────────────┘
```

- **Manager**: a Gradle subproject (`manager/`) in the same repo, written in Java 25. It owns all state in `/data`.
- **Local UI preview**: Vite's `/api` proxy preserves the browser's Host header, including WebSocket upgrades, so the manager's same-origin check accepts live updates. For LAN browsing, the built UI (`npm run preview -- --host 0.0.0.0`) avoids the large development module graph and its slow first render.
- **Web UI startup** (2026-10-29, for slow high-latency links like Tailscale on weak Wi-Fi):
  - `app.html` carries a skeleton of the shell (logo, neutral blocks, nothing user-specific) with its own inline CSS, so it paints before any script or API response. It is a fixed overlay with `role="status"`, its pulse respects reduced motion, and it shows "Couldn't load ZenithHub" with Try again if a script fails, or "Still loading…" after 20 s. The layout calls `zenithBoot.loading()`: the overlay stays until the login screen, the dashboard (session and overview loaded) or an error with Try again can show, and returns while the overview loads after signing in.
  - An inline script asks for `/api/session` and `/api/overview` at once while the scripts download; `api.prefetched()` uses those answers once (a signed-out overview 401 is thrown away), anything else is asked for again.
  - `web/scripts/finish-build.js` (part of `npm run build`) makes the stylesheet non-blocking (preload plus `media="print"`; the skeleton waits for it) and preloads the error page and the current route's scripts by path. `vite.config.ts` puts the root layout's and error page's static imports in one startup chunk and small modules several pages share in one `common` chunk; other route code stays split.
  - Cache headers: `/_app/immutable/*` is `public, max-age=31536000, immutable`; HTML, the SPA fallback and other static files are `no-cache`; every `/api` response is `no-store`. Missing `/_app/` files are real 404s, not the HTML page. The favicon is an inline data URI.
  - Measured at 350 ms RTT and 3 Mbps, signed in: startup requests went from 36 (depth 3) to 15 (depth 2). The first paint (the skeleton) went from about 3.4 s to 0.4 s, and the dashboard showed at about 1.5 s cold (was 3.4 s) and about 0.75 s warm (was 3.3 s, when every asset was revalidated). Network stalls still show as the skeleton, not a blank page.
- **Zenith instances**: unmodified behaviour apart from **managed mode** (`ZENITH_MANAGED=1`). Messages that would tell users to type a command name the web UI's settings instead, or are left out where ZenithHub has no such setting (chat schemas, plugins):
  - a localhost HTTP control API (status, commands, config defaults), authenticated with a per-process token;
  - no interactive terminal, no self-updater and no per-instance Discord bot;
  - logs go to stdout, where the manager captures and streams them;
  - no device-code prompts inside instances: the manager owns MSA login, refreshes tokens and syncs `mc_auth_cache.json`.
- **Updates**: Docker image tags only. CI (`.github/workflows/ci.yml`) publishes `ghcr.io/jkramer5103/zenithhub` (`latest`, `sha-<commit>`) from `main`. The image builds while the tests run, and `latest` only moves once they pass. Docs-only changes skip CI. There is no self-update.
- **Cheats start off**: even without the switch, those same modules (AutoTotem, AutoEat, AntiAFK, AutoRespawn and the rest of the list; TickRate keeps Zenith's default) are off in ZenithHub's defaults layer (`instances/Cheats.offByDefault`, applied wherever Zenith's defaults are read), so every account starts as a plain client. Global, server or instance settings can turn each one on (decided 2026-10-29).
- **No-cheats switch**: `ZENITH_DISABLE_CHEATS=true` on the container turns off KillAura, SpawnPatrol, TickRate, AutoTotem, AutoArmor, AutoMend, Spook, AntiAFK, AutoFish, AutoEat, AutoOmen, AutoDrop, AutoRespawn, Spammer and AutoReply (decided 2026-10-29; Pathfinder, PearlLoader, AutoDisconnect, VisualRange, Tasks and spectating stay). Zenith (`com.zenith.control.Cheats`) refuses to enable those modules and drops their commands; the manager (`instances/Cheats`) forces them off, hides their settings and rejects writes, keeping existing overrides for when the switch is removed. The settings editor shows a note.
- **Reconnect randomness** (fork change in Zenith, 2026-10-29): `client.extra.autoReconnect.randomSeconds` makes each auto reconnect wait `delaySeconds ± random`, and `client.maxPlaytimeReconnectRandomMins` makes each scheduled-reconnect session last `maxPlaytimeReconnectMins ± random`, re-rolled per connection and when the settings change. Both default to 0, which keeps upstream behaviour. They are under Settings → Connection, and `autoReconnect random <seconds>` is the command. Reconnects started by Active hours or the reconnect command keep their fixed delays.

## Data model (`/data/manager/state.json`)

| Entity   | Fields |
|----------|--------|
| User     | id, username, password hash (PBKDF2), admin flag, linked MC names, linked Discord ID |
| Account  | id, type (`msa` / `offline`), MC username + UUID; auth cache at `/data/accounts/<id>/mc_auth_cache.json` (0600) |
| Server   | id, name, address, port, settings overrides |
| Instance | id, name, accountId, serverId, settings overrides, lifecycle (`desiredRunning`, autostart policy), grants |
| Grant    | subject (`user:<id>` / `mc:<name>` / `discord:<id>`), role (Viewer, Player, Spectator, Operator, Admin), extra capabilities |

The admin is a superuser: they see every instance, can join any of them in-game, and have every right.

### Settings layering

`Zenith defaults → Global → Server → Instance → forced managed values`

- Zenith writes its defaults (`config.defaults.json`) on start in managed mode.
- Settings changed inside an instance (by commands or in-game) are diffed against `defaults⊕global⊕server` when it stops, and saved as instance overrides. In-game changes therefore persist and are never clobbered. A global or server change that couldn't be pushed to a live process (it was starting, or didn't answer) is remembered per path until the next spawn or a later successful push, and those paths keep the instance's previous override instead of turning the stale value into one.
- Some values are always forced by the manager: bind address and port, target server, account, and turning off Discord, the terminal and the updater.

## Phases

### Phase 1: Foundation (done)
- [x] Zenith managed mode + control API (`com.zenith.control`). Status `online` means in the game (the client's login handled, not in a queue), not just a TCP connection; health, food and position are only sent then. The manager keeps only the newest of overlapping status polls and clears the status after three failed polls in a row.
- [x] Manager: state store, settings layering, supervisor (crash restart with backoff, restore previous state on boot)
- [x] Accounts: MSA device code (shown in the UI), auth-cache import, offline; background token refresh. Add account and re-login group cookie, Minecraft access-token and Microsoft refresh-token login under **More**. Cookies accept login.live.com Cookie headers or Netscape exports, including files with an account summary and separate access token above the cookie rows; only the Microsoft cookie rows are used. Netscape rows with empty values work with or without a final tab, including unrelated browser cookies in the export. Cookies are exchanged without being saved. Cookie exchange uses the Xbox sign-in/offline-access scopes for renewable authorization-code sessions. It follows Microsoft's hidden continuation forms and handles first-use Minecraft Launcher consent (including script-rendered consent) only for those two scopes and the official client ID, preserving the return query and cookie domain boundaries. The form explains the permissions before submission. Password, MFA and other interactive requirements are reported explicitly rather than as malformed credentials. Cookie imports never silently fall back to an embedded Minecraft access token. Refresh tokens can specify their issuing application client ID. Access-token sessions last until expiry and require re-login: the account stores `tokenExpiresAt`, and the Accounts page shows the countdown and an "Access token" badge instead of the refresh button. The form recognises a pasted token, cookie set or refresh token and switches to that method. All methods verify the Minecraft profile before saving.
- [x] Ownership: every user adds their own accounts and private servers; owners have full access; "Yours" vs "<owner>'s" everywhere (web, lobby, Discord)
- [x] Minecraft linking: code shown in-game (kick screen / lobby menu item), entered on the web; linked names act as the user
- [x] Discord shows Zenith's original embeds, forwarded through `/v1/events`; mentions ping the owner. Every notification can be switched off under Settings → Discord. No chat relay.
- [x] Web auth: first-run admin setup, login sessions, role/grant model in place. Logins, wrong current passwords and wrong Minecraft link codes are throttled per user (and logins per IP). Changing your password signs out your other sessions.
- [x] REST + WebSocket API: instances CRUD, start/stop/restart, status, live console, run command
- [x] Web UI v1: setup/login, dashboard, add account, add server, add instance, instance page (console, chat, commands, start/stop)
- [x] Dockerfile (multi-stage: GraalVM native Zenith + manager + UI) and `docker-compose.yml`

### Phase 2: Settings + users (done)
No commands needed anywhere: the console only shows in developer mode (user menu, stored per browser).
- [x] Zenith: `ZENITH_DUMP_SCHEMA` writes config defaults + typed schema; control API `GET/POST /v1/config` changes settings live (reflection, validated before applying)
- [x] Manager: settings API per layer (`/api/settings/global`, `/api/servers/{id}/settings`, `/api/instances/{id}/settings`); values, sources, forced paths; changes pushed to running instances; Mojang name lookup for player lists
- [x] Curated settings pages (connection, survival, safety, AFK, combat, chat, joining, extras) at all three layers, with search, "changed" filter and reset to inherited
- [x] Generic editor for every setting, in developer mode
- [x] Instance page tabs: Overview (status + chat), Settings, Console (developer mode)
- [x] Outbound proxy for everything, not just the server connection. Settings → General has the **global proxy** (the global layer's `client.connectionProxy`, so it's off the Defaults tab) and, as a separate switch, **Let users set their own proxy** (`userProxiesAllowed`; old state files' `outboundProxiesEnabled` loads into it). Off: `ConfigComposer` forces every instance (and the server layer) to the global proxy exactly, or no proxy while it's off. On: users can change the proxy at server or instance level, but while the global proxy is on `enabled` stays forced, so they can't turn it off. The global login (user and password) is blanked for any instance pointed at a different type, host or port, so it never reaches someone else's proxy. Settings views mask the global password outside the global layer, and saving one proxy field pushes the whole proxy block to running instances.
  - Bot: while the proxy is on, `com.zenith.control.OutboundProxy` sends all of its traffic through it: MCProtocolLib's TCP connection, the session server join (`SESSION_SERVICE_KEY`), MSA/Xbox sign-in (`Authenticator`), every `Api` (skins, Mojang, Minotar…), the version-detection and queue pings (`Pinger`) and resource packs. It never falls back to a direct connection.
  - Manager: an account's sign-in and token refreshes use the proxy of its oldest instance; new sign-ins and player lookups use the global proxy (`OutboundProxies`). Discord stays direct. DNS SRV lookups for the server address still run locally.
  - Java's `HttpClient` can't use SOCKS, and Java's proxy logins apply to the whole process, so HTTP clients point at a `ProxyRelay`: a plain HTTP proxy on 127.0.0.1 that does the SOCKS5/SOCKS4/HTTP CONNECT handshake (with login) per connection and lets the proxy resolve host names. The bot and the manager each have a copy of it.
- [x] Users and sharing UI: role presets + custom capabilities; share by MC name or Discord user without a web login
- [x] Editors for structured lists (waypoints, active hours, pearl loader, server switcher)
- [x] The "Who can play" / spectator whitelist sections are gone; grants decide who may join

### Phase 3: Lobby (done)
- [x] Router on the public MC port (`ZENITH_LOBBY_PORT`, default 25565). Status pings and normal logins go to the lobby. Transfers carrying a `zenith:target` cookie are piped to that instance's localhost port.
- [x] Void lobby (MCProtocolLib, online mode) with a chest menu: one player head per instance the player may join, with its status in the tooltip. Left-click plays, right-click spectates; an offline instance is started first if the player may control it. The compass reopens the menu.
- [x] Clicking sends a Transfer with cookies `zenith:target`, `zenith:zenith-transfer-src=lobby` and `zenith:zenith-spectator`. Zenith's `proxyIP` is forced to the public address, so `/lobby` and spectator swaps come back through the router. Spectators can always use `/lobby` (and `!lobby`), even with Zenith's spectator commands off; their command tree then holds only `lobby`. The start-up connection test is forced off: it pinged that address through an outside status service, which can't reach a LAN address and learns the address.
- [x] Instances enable client-side ViaVersion by default (`client.viaversion.enabled`) and join each server at the newest version it supports. Multi-version servers answer Zenith's discovery ping (protocol -1) with their oldest version, so `ProtocolVersionDetector` pings again with the newest release Via knows and uses it when the server echoes it back (otherwise e.g. HugoSMP saw an old version and refused its dialog menus). Zenith itself is native 26.3 (merged from upstream's `26.3.0` branch, decided 2026-10-30) so menus, dialogs and other new features reach 26.3 players untranslated; with 1.21.4 in the middle HugoSMP's /settings dialog was squeezed into a ViaBackwards chest menu. For older servers and older players ViaBackwards still turns dialogs into chest menus; it reads some dialog labels with a text codec that doesn't know the `custom`/`show_dialog` click events before rewriting them, which disconnected us, so `ZenithDialogViewProvider` rewrites those labels first. MCProtocolLib 26.3.0.5 writes `custom_click_action` (dialog button clicks) with its payload twice, so servers kicked the player; `McplPacketFixes` registers a correct serializer at startup (remove once fixed upstream). The manager reads the Zenith defaults before restoring instances, so changed defaults apply after an image update.
- [x] Clients from 1.20.5 (the first version with transfers) up to the newest version ViaVersion knows (26.3 with Via 5.12.1). The lobby embeds ViaVersion and ViaBackwards and translates to its own 1.21.4; instances translate transferred clients with Zenith's own server-side Via. Older and unknown versions get a clear message, and their server list shows the lobby as incompatible. Players without any grant are kicked with "You are not whitelisted on this server."
- [x] Zenith's whitelist and spectator whitelist are forced from grants (name→UUID directory in `/data/manager/players.json`) and pushed live when grants change.
- `ZENITH_LOBBY_ONLINE_MODE=false` exists for local testing only.

### Phase 4: Central Discord bot (done, optional)
- [x] One bot token, set on the Settings page (stored 0600 in `/data/manager/secrets`, never returned by the API); enable switch, status and invite link.
- [x] Category per account, channel per instance, created and cleaned up automatically; member overrides synced from grants and linked users.
- [x] Discord linking with a one-time code (`/link CODE`, 10 minutes) from the user menu; unlink in the same dialog.
- [x] Slash commands in an instance channel (`/status`, `/start`, `/stop`, `/connect`, `/disconnect`, `/command`, `/pearl`), checked against the linked user's capabilities.
- Not yet tested against a live Discord server.
- **Looking like a vanilla client** (fork changes in Zenith, 2026-10-29; settings under Settings → Privacy, `client.privacy.*`):
  - On by default:
    - Client settings like a fresh install (locale `client.privacy.clientLocale`, view distance 8/10/12/16 and main hand picked once per account from its name, particles all, server listing on). The bot's settings stay put while a player is connected (`steadyClientInfo`).
    - Chat signing like vanilla: a random session ID, a random salt per message, and last-seen tracking (`cache/data/chat/LastSeenMessages`). Signed messages and commands include the acknowledgements, and a chat ack goes out every 64 messages. Before this, busy secure-chat servers could kick the bot for never acknowledging. Players' own chat acks are dropped, because Zenith re-signs their messages with its own session.
    - Known packs: Zenith claims `minecraft:core:<native version>` when the server offers it and fills the entries the server leaves out from `mcdata/core-registries.bin.gz` (captured from the vanilla 26.3 server by sending an empty known-packs reply and recording the registry data; `CoreRegistryData`; `scripts/capture-core-registries.py`; `mcdata/en_us.json.gz` comes from the 26.3 client jar). Recapture both whenever the native version moves, or Zenith claims a pack it can't fill. Through ViaVersion the server offers its own version's pack, so the reply stays empty, as from a vanilla client of our version.
    - Cookies are stored and answered (`ClientCookies`), and a transfer reconnects with the TRANSFER intent and keeps them.
    - Ping requests are off (`client.ping.sendPingRequests`), and the ping comes from the server's tab list.
    - Keep-alive and ping replies go out at the start of the next client tick, not instantly.
    - Resource packs are really downloaded (`ResourcePackDownloader`): vanilla's headers, redirects, a SHA-1 check, a 250 MB cap and a cache of the last 8 packs in `resource-packs/`. The statuses are spaced out like a download plus reload.
    - When the bot takes over from a player it keeps their ground state and momentum (`PlayerCache.recordMove`, `smoothHandoff`).
  - Off by default (ideas from the OpSec mod; `com.zenith.control.Privacy`):
    - drop players' custom payloads (`vanillaSpoof`)
    - block cookies
    - refuse packs from private networks, also after redirects and in packs sent on to players, unless the server itself is local
    - placeholder name and UUID in pack downloads
    - answer sign translation/keybind probes with what an unmodded en_us client with default keys renders (`VanillaText`, using vanilla's full `mcdata/en_us.json.gz`)
    - strip skins and capes not hosted on textures.minecraft.net from the tab list sent to players
  - Not done: anvil rename probes.
  - The Control tab's More view has a **What the server sees** card (CONTROL) from `/v1/details` → `fingerprint`, with a link to the Privacy settings (`?tab=settings#settings-privacy` scrolls to the group).

### Phase 5: Controls, pearls and tasks (done, 2026-10-29)
Everything a user did with commands now has a UI, except lookups (seen, stats, …), plugins and map rendering, which aren't supported.
- [x] Zenith control API `GET /v1/details`: inventory or open container (slot numbers as Zenith's inventory command uses them), pathfinder state, replay recording, scheduled tasks. Command results flag error embeds (`embed.error`, the theme's error colour).
- [x] Manager `POST /api/instances/{id}/action`: structured actions (`instances/Actions`) turn into Zenith commands. Every argument is checked against a strict pattern, and each action names the capability it needs: movement, clicking, inventory and looking need PLAY; requeue, kick, transfer, recording and tasks need CONTROL; waypoints need SETTINGS; free text (`command`) needs COMMANDS and only shows in developer mode. A task wraps another action and needs CONTROL plus that action's capability.
- [x] Instance tabs: **Control** (movement modes, waypoints, clicking, looking, respawn, inventory grid with hold/move/drop and container take/put, players with kick and transfer, requeue, recording with download), **Pearls**, **Tasks** (once later, repeating, or on an event; built from the same actions). Details are polled every 2 s while a tab is open.
- [x] Stasis pearls: a `PEARLS` capability ("Load stasis pearls", in every role from Spectator up) loads any of the instance's pearls. The list is the PearlLoader setting; people with SETTINGS add, edit and remove pearls in the Pearls tab. Discord `/pearl <pearl>` (with autocomplete) in the instance channel.
- [x] Pearl webhooks: in developer mode each person gets their own secret URL per pearl (`/hooks/pearl/<token>`, 192 random bits, stored 0600 in `secrets/pearl-webhooks.json`). POST loads the pearl as that person and only while they still have PEARLS; GET shows a button, so link previews load nothing. 5 s cooldown per URL. New URL replaces the old one; deleting the instance or the user drops them.
- [x] Connected players card (Control tab, CONTROL): everyone connected through the proxy, playing or spectating, with one-click Kick, Kick everyone, **Make player** (a spectator takes over; whoever was playing starts spectating) and **Make spectator**. The managed-only Zenith command `controller set <player>` / `controller release` does the swap with the same transfers as the in-game `swap force`, and only accepts the manager as source. Make player is greyed out, with the reason shown, for spectators without play access and clients older than 1.20.5.
- [x] Connection history (collapsible under Connected players, CONTROL): Zenith's control API sends `player` events (joined/left, player or spectator, disconnect reason) over `/v1/events`. `PlayerHistory` keeps the last 200 per instance in `manager/history/<id>.json`, merges a leave and rejoin of the same name within 15 s into one "switched" entry when the role changed (a plain relog stays a leave and a join), and names who kicked or swapped from the web UI. Transfer reasons are dropped. `GET /api/instances/{id}/history`; deleting the instance deletes its history.
- [x] Nearby players card (Control tab): other players in the bot's visual range from `/v1/details` (`nearby`: tab-list name, position, distance, friend), nearest first, with distance, compass direction, coordinates and, with PLAY, **Follow** and **Go to**.
- [x] Control tab layout: an activity bar on top (what the bot is doing: moving, holding a click, recording; position; one **Stop** that ends pathing and held clicks; `/v1/details` reports `clicking`), then four views so nothing is a long scroll away on a phone: **Move** (Go to, Fly, Follow and Mine up front, the other modes behind "More"; waypoints beside it), **Players** (connected players with history, nearby players), **Inventory**, and **More** (click and look, with exact angles folded away; transfer and requeue; recording). The view is kept in `?view=`, and views the user has no capability for are hidden.
- [x] Settings cover every Zenith setting. The rarely used ones (plus the Network and Troubleshooting sections) carry an Advanced tag and stay hidden until "Show advanced settings" is switched on (per browser, `localStorage.settingsAdvanced`). Search always finds them.
- [x] Recordings: `/api/instances/{id}/replays` lists, downloads and deletes the `.mcpr` files in the instance's `replays` folder (CONTROL).

### Phase 6: AFK zones and proxy pooling (done, 2026-10-30)
For plugin servers like HugoSMP and DonutSMP that pay for idling in an AFK zone.
- [x] `ServerScreen` (bot): what the server shows besides chat, as plain text: sidebar (scores sorted like the vanilla client, text from the display component or the owner's team prefix and suffix), boss bars, action bar (5 s), title and subtitle (10 s), tab header and footer. Icons drawn with resource-pack fonts (private use characters, Yi syllables on HugoSMP) are stripped. In `/v1/details` as `screen`.
- [x] `AfkZone` module (bot, always on, settings under `client.afkZone`): sends the enter command (`/afk`) after a random 8–30 s wait and counts the stay as started when a title, subtitle or action bar contains the confirmation text ("AFK"). With **keep** on it goes back in after every connect and whenever it ends up outside, and pauses while a player controls the account. A new login packet (a backend switch), a dimension change or moving more than `leaveDistance` blocks from where it entered counts as having left. No confirmation within 30 s means another try after 45–120 s, up to `maxAttempts`, then Couldn't get in. It reads the reward from the sidebar line with `rewardLabel` (Stars), with k/m/Mio/Mrd and either decimal separator. **Earning** is false while the zone message contains `notEarningText` ("verifiziert": HugoSMP's Discord verification hint) or when the counter hasn't risen 4 minutes in, and true once it has risen. States: OFFLINE, OUTSIDE, WAITING, ENTERING, IN_ZONE, PLAYING, FAILED. `afkZone keep on|off`, `afkZone enter`, `afkZone leave` (leave turns keep off); actions `afkKeep` (CONTROL), `afkEnter` and `afkLeave` (PLAY). Changes go to the manager as `afk` events.
- [x] `AfkHistory` (manager): the counter at most every 5 minutes for 14 days plus a moving last point, and the last 100 stays (start, end, reward at both ends, why it ended) in `manager/afk/<id>.json`. `GET /api/instances/{id}/afk` (VIEW).
- [x] **AFK** instance tab (PLAY or CONTROL): state with the countdown to the next try, a clear Not earning warning with the server's own words, Earning with the live server message, the counter now, this stay and per hour, keep switch, Go in now and Leave, the counter chart, past stays, and the server's sidebar. Setup lives in Settings → AFK → AFK zone, so it can be set per server.
- [x] DNS: `HostResolver` follows the CNAME with netty's DNS client when the system resolver answers an A query with nothing (some routers do for CNAME chains like `java.hugosmp.net`), for the MCPL connection (`CLIENT_BOOTSTRAP_INITIALIZER`) and the pings.
- [x] Proxy pool (Settings → General, admin): a list URL from a provider (Webshare's download link and the like; `host:port`, `host:port:user:password` or `scheme://user:password@host:port` per line). The URL and the downloaded list are 0600 secrets (`secrets/proxy-pool-url`, `secrets/proxy-pool.txt`); the API never returns them, only `host:port` per account. Each account gets a free proxy at random the first time it's composed and keeps it while the list has it (`state.proxyPool.assignments`); all instances of an account share it. While the pool is on, `ConfigComposer` forces the account's proxy over the global and users' own proxies, and the password is blanked in instance settings views. An account with no free proxy left doesn't start rather than share one or connect directly. The list is read again every 6 hours (through the global proxy while it's on); an account whose proxy left the list gets a new one when it next connects. Per account, **Shuffle** gives it a different proxy; **Reconnect everyone now** restarts the connected instances one every 5 s so they switch at once. New sign-ins of accounts without an instance still use the global proxy.

### Phase 7: Task triggers and Notify me (done, 2026-10-31)
- [x] `TriggerCondition` (bot, `com.zenith.control`): a task condition with settings, saved as one spec string (`kind;key=value;…`, e.g. `player;who=stranger;cooldown=60`) in `ConditionTypeAdapter` as `{type: TriggerCondition, data: {spec}}`. `tasks add trigger <id> <spec> <repeat/once> <command>`. Kinds: `afk` (`on=earningStopped|earningStarted|leftZone`), `player` (`who=anyone|stranger|<name>`, from VisualRange enter events; stranger means not on the friends list), `health` (`below=` 1–19 health points, fires on crossing and rearms 1 heart above), `attacked`, `totem` (our own pops only), `daily` (`at=HH:mm`, `days=` ISO weekday digits, `zone=`, `jitter=` up to N minutes later; runs missed while the bot was off are skipped, a time a clock change skips moves to just after it), `unattended` (`minutes=`; counts while in the game since it got in or a player last controlled it), `arrived` (`x`, `z`, `radius`; fires on entering the circle, not when already inside) and `onlineFor` (`minutes=`, from the connect). They all fire on a change, never again while the state lasts. Common settings: `cooldown` (seconds, at least 10, default 60: the task runs at most that often), `delay` (a random wait of up to N seconds before running), `ifIdle=1` (skip it if a player controls the account when it's time). `/v1/details` reports them as `type: trigger` with the spec and, for daily, `next`.
- [x] Manager: `addTask` takes `when: trigger` with a `trigger` object and builds the spec from checked values (`Actions.trigger`); the bot checks it again. Action `notify` (CONTROL) with a message of up to 200 characters runs the bot's `notify` command: an `alert` event for the owner's browser (WebSocket; only the instance's owner gets it) and a Discord embed unless `discord.notifications.taskAlerts` is off, with a ping unless `taskAlertsMention` is off (Settings → Discord). The web UI shows alerts as a 20 s toast and, when the tab is hidden and the user allowed it (https or localhost only), as a system notification.
- [x] Tasks tab: four kinds of When (Once later, Repeat, At a time, When…). When… groups Zenith's events and the triggers, with their settings; At a time has a time, weekdays and a random offset in the browser's time zone. Options: at most once every…, a random wait, and Only if nobody is playing (on by default for actions that move or click). Notify me, Go into the AFK zone and Leave the AFK zone are new task actions.
- [x] `client.viaversion.enabled` is forced on: without it a bot speaks only Zenith's native version and reconnects forever with "Outdated server" anywhere else. The switch is gone from Settings.
- [x] LAN servers connect directly: `ConfigComposer.isLanAddress` (IPv4/IPv6 literals in loopback, private, link-local and `fc00::/7`, `localhost`, names without a dot, `.local`/`.lan`/`.internal`/`.home.arpa`/`.localdomain`; no DNS lookup, so nothing leaks around the proxy) makes `ConfigComposer` force `client.connectionProxy.enabled=false` over the pool, the global proxy, users' own proxies and overrides, and the pool assigns no proxy for it.
- [x] Admin proxy override per account (Settings → General, proxy pool card, the sliders button on each account): Default, No proxy, or a custom SOCKS5/SOCKS4/HTTP proxy. Kept in the 0600 secret `secrets/proxy-overrides.json` (`ProxyOverrides`); the API returns it without the password (`hasPassword`), and a blank password keeps the saved one. It wins over the pool (which frees the account's pool proxy), the global proxy and the owner's own; owners can't see or change it. `PUT`/`DELETE /api/proxy-overrides/{accountId}`, admin only; deleting the account deletes it.
